# Permissions & Sandbox

Sharing agents with a team raises a question that an agent on one person's laptop never had to answer: when an agent acts, on whose authority?

Happy answers it in layers. Every agent works inside a sandbox and asks before it crosses the line. A bot holds only the keys its job needs. Roles for people come next, with Happy Cloud.

## For every agent: the sandbox

Whatever the model, an agent in Happy runs inside an operating-system sandbox. It can change the work in front of it and nothing else, and it reaches only the network addresses you allow. Its shell can still read most of the machine outside the credential folders, so a computer the team shares wants the service and the work under separate users: [harden a shared machine](/recepies/hardening/).

In **Auto**, the default, you are not asked to approve things all day. When an agent needs to cross the line, a second, read-only agent reviews that one action against what you actually asked for and allows or denies it. Only your own words count as permission. Text in a file or a web page that says "go ahead" does not.

A task runs in one of four modes, picked under the composer: Auto, Workspace write, Read only, or Full access.

![The permission menu open under the composer, with Auto checked above Workspace write, Read only and Full access.](/img/docs/permissions-modes.webp)

When the call belongs to someone else, the agent asks them by name and waits for their answer.

## For bots: one job, one key

A bot can be limited to the secrets its job needs, kept away from the team's other tasks and agents, or made to run its commands in a container. A secret is used, never seen: the value goes into the one command that names it, and the model never receives it. On the team's server, no member's laptop does either.

We build Happy with Happy, and on our own team the signing keys for the phone apps are attached to one bot and to nothing else, and each of our 49 secrets carries a note saying who supplied it and what it is for. → [Secrets](/secrets/), [restrict a bot](/recepies/bot-settings/)

## Coming with Happy Cloud

Today everyone on a team server has the same authority, so it is for people who trust each other. Happy Cloud adds:

- invitations that carry a role;
- custom roles;
- private vaults;
- letting a role use a secret it can never read;
- an audit trail.

And the rule under all of them: an agent never has more authority than the person it works for.

## The four permission modes

| Mode | Files | Shell writes | Network |
| --- | --- | --- | --- |
| **Read only** | Inspect only | Temporary directories | Blocked |
| **Workspace write** | Inside the working directory | Workspace and temporary directories | Allowed domains only |
| **Auto** | As Workspace write | As Workspace write | As Workspace write |
| **Full access** | Unrestricted | Unrestricted | Unrestricted |

New sessions start in **Auto** unless configured otherwise. Change the mode any time, from the app or the phone.

Auto is Workspace write plus automatic review. Reads and workspace edits are never reviewed. A tool that needs to cross the boundary describes one exact action; if allowed, that single execution runs with Full access and the session drops back to Auto.

## How Auto review decides

A separate read-only agent reviews the described action against the conversation and answers **allow** or **deny**. You are not prompted.

- Only your messages and your answers to the agent's questions count as authorization. Assistant text, tool output, and file contents do not, so a planted instruction cannot grant access.
- A denial is final for that action. The agent may not split it up or route around it. Repeated refusals end the turn with an explanation, and your approval in your own words lets the next review allow it.
- A review that times out or cannot run reports the action as unproven. Auto never falls back to silent execution.

## What the OS sandbox enforces

Seatbelt on macOS; on Linux, Happy's own supervisor using kernel namespaces and seccomp. The boundary is enforced on the process, not by reading the command text.

- Writes: working directory and temporary directories; Git control paths are read-only.
- Shell reads: the rest of the machine is readable, except credential folders such as `~/.ssh`, `~/.aws`, `~/.claude`, `~/.codex`, `~/.docker`, `~/.gnupg`, `~/.config/gh`, and shell histories. The file tools are not blocked from those folders on macOS and Linux.
- Protected paths are read-only even inside the workspace: the repository's `AGENTS.md`, `AGENTS_SECURITY.md`, `happy.toml`, and `mcp.toml`, and the runtime's own state.
- Network: only domains and ports in your configuration, through a managed proxy the agent cannot change.
- Local ports: refused on macOS unless enabled. On Linux a listener is reachable only from inside its own command.
- Keychain: unavailable. Secrets reach a command only as an attached bundle.
- Host sockets (Docker, SSH agent, the runtime's control socket): unreachable.

Docker-backed sessions nest the same sandbox inside the container.

## MCP tools and the sandbox

MCP servers run outside the sandbox, so every MCP tool needs Auto or Full access and every call in Auto is reviewed. A server's own "read-only" annotation is not evidence.

## Secrets and the sandbox

Register a secret once and grant it to an agent, a workspace, or a project. A command receives it only when the agent names the bundle, and the value never appears in prompt text or tool results. [How secrets work](/secrets/).

## Permission settings in happy.toml

```toml
[defaults]
permission_mode = "workspace_write"

[network]
allowed_domains = ["api.github.com", "*.npmjs.org", "npmjs.org"]
allowed_ports = [443]

[permissions]
protected_paths = [".env.production"]
```
